# 余烬服务器：全面审查与整改建议

**日期：2026-10-04｜对象：Picadoo/ember-server｜性质：代码与规则审查，不是上线验收**

审查基线：`40441253f5f4e0aa1722ed3c5da0821b1e86256c`（简称 `4044125`）。该提交的源码版本是 CoreRpg 1.62.0；交接文档仍记载 1.61.0 在线，并提到尚未部署的 D150。本文不据此认定 1.62.0 已部署，也不把不同版本的测试结果混为一谈。[S01] [S02]

本报告只提出建议。没有修改玩法代码、数值、数据库、线上配置或权限设置。配套本地验证只执行了隔离的规则代码与算例；没有登录游戏服，没有运行完整 Maven、p1sim、p2econ 或多人实服测试。

## 01 结论：方向正确，但验证能力已经落后于功能增长

**项目不是在虚假繁荣。分工、实际配置驱动的模拟、评审反馈和后续修正已经形成了一部分有效闭环。但目前还不能把“模拟通过、冒烟通过”解释为“资产安全、数值可靠、游戏好玩都已证明”。**

数值模拟是应当保留的核心能力。`p1config` 会读取实际配置和部分 Java 常量，`selfcheck` 检查主线配置与怪物生命的一致性；成长终验有对照、参数调整与冻结记录。这比让不同 AI 分别凭感觉写数字更可靠。[S16] [S19] [S20]

真正需要补的是三件事：

1. **资产操作必须可恢复。** 1.62.0 新仓库把装备状态、材料余额、实体背包和数据库回调连接起来，暴露出离线与失败时的交付缺口。
2. **模拟必须先证明自己算的是同一个游戏。** 本轮定位到了未受控随机源、对照组随机流错位、多人燃烧表示差异，不应继续把这些差异当一般随机噪声。
3. **成长既要不失控，也要值得投入。** “所有新增系统影响都极小”不是唯一正确目标。主成长负责明显变强；小幅侧向调整应低摩擦、低试错成本。

**建议继续当前方向，不重写整套策划，不新增第四套装和新的永久战力槽。下一阶段优先完成“资产可靠性＋模拟可信度＋投入体感”三个工作包，而不是继续铺新系统。**

### 阅读顺序

服主先看本节、第 02 节问题总表和第 09 节行动顺序；模拟负责人重点看第 04、05、08 节；插件负责人重点看第 03、06 节；地图与测试负责人看第 07 节。每项建议均区分证据、影响和验收条件，不要求同时开工。

## 02 范围、证据等级与问题总表

### 2.1 本轮实际做了什么

通过 GitHub 连接核查当前提交、分支状态和相关源码，重点覆盖数值加载、团本模拟、成长检查、套装运行时、装备库、材料仓、数据库事务、背包快照及测试记录。公开下载在本环境没有成功，因此没有把完整仓库搬入本地或声称做了全仓编译。

本地独立验证包括八组规则检查。其中 `EmberBurnBook.java` 和 `EmberSetRules.java` 是从连接读取的完整原始文本，重新计算的 Git blob SHA 与仓库一致，之后用 `javac` 编译并运行专用测试。其余为精确摘取的短类、缩小的随机流重现或独立算术，详见第 08 节。

不在本轮已验证范围内：真实世界存档与地图观感、生产数据库内容、在线部署状态、全部外部插件、并发负载、完整交易安全、真人留存、付费记录和法律合规。没有证据的部分不会写成已经通过或已经出事故。

### 2.2 如何理解优先级

**P0**：相关新功能公开使用前应阻断的资产交付缺口，不表示已发现线上事故或任意玩家可稳定利用。

**P1**：影响数值裁决、资产一致性或验收可信度，应在继续依赖该结果前处理。

**P2**：策划取舍、维护与统计表达问题，排在基础可靠性之后。

证据标签：**已定位**表示源码明确存在该路径；**已重现**表示本轮隔离验证确认了具体行为；**条件风险**表示依赖故障或操作前提，仍需集成测试；**设计判断**表示建议而非代码错误。

## 03 资产与存储：1.62.0 新增功能应先补交付闭环

### A01｜离线后，装备状态已变而玩家未收到结果

`EmberGearLib` 的相关分支是明确的：[S04]

- `stashSlot` 先移除背包物品再提交数据库事务；失败回调时若玩家离线，只记录原物品未返还。
- `withdraw` 把数据库状态从 `stored` 改为 `active`；回调发现玩家离线，只记“row active, no stack”并指向管理员恢复。
- `bulkDone` 在分解事务已经完成后发胚料；玩家离线则直接返回并记录“blanks not given”。
- 撤销分解先扣胚料，失败时的退款也依赖玩家仍在线。

**问题是交付闭环缺失，不是 SQL 事务完全不存在。** 当前 `commitTxn` 已有请求唯一键、行锁、版本号与状态检查，这是值得保留的基础。但它保证的是装备行变化，不是玩家一定拿到对应物品或材料。[S05]

管理员可以恢复一部分丢失装备，不等于系统已经具备自动补投递。尤其批量分解的材料不应只存在于回调里的计数器。

**建议：** 把“装备状态变更＋应发材料／应退款／待投递物品”写入同一个持久业务请求。在线时投递，离线时保留，登录后重试同一结果。交付唯一键至少包含玩家、请求、产物序号。不要重新随机产物，也不要只靠日志补账。

**验收：** 在提交前、数据库提交后回调前、投递后确认前分别模拟断线或进程终止。重连与重启后，用户最终恰好收到一次结果；不允许“装备已分解、材料未发”，也不允许重试重复发放。这里只要求测试环境故障注入，不能直接在正式服试。

### A02｜自动入库的“成功”早于数据库成功

`autoStash` 顺序调用 `upsertItem`、`logCreate`、`saveLibFlags`，随后更新缓存、返回 `true`。这些 SQL 任务异步排队，`EmberItemStore.run` 捕获异常后记录告警，却不把成功／失败结果传回该调用者。[S04] [S05]

因此，**代码已走“没有生成实体物品，已入库”的分支，并不意味着装备记录一定持久化成功**。数据库在操作中断开、表初始化失败或写入失败时，需要额外恢复链。当前读到的自动入库路径没有等待该确认。

**建议：** 区分 `PENDING`、`PERSISTED`、`DELIVERED`，而不是用一个布尔值同时表达接受请求与持久化成功。自动入库失败不能静默丢结果，也不能未经去重直接再发一件新装备。新掉落应先有稳定的物品 UID 和持久产物记录。

**验收：** 单独让装备行写入、创建日志写入、收藏／锁定标记写入失败，验证重试不产生“有日志无物品”或“缓存显示有、重登变没有”。恢复后的状态必须可由数据库重新构建，不能依赖进程内缓存。

### A03｜材料余额和装备行之间仍有跨系统事务缝隙

材料仓复用 `PlayerData` 仓库槽；增减先发生在内存，`flushSoon` 延后 40 tick 调用持久化。按正常 20 TPS 约为两秒，但这不是故障时的最大持久化延迟保证。[S06]

`commitTxn` 中的 `cost_json` 是日志字段；抽查到的数据库事务修改装备行和事务日志，并没有在该事务内同时扣除全部材料、金币与实体背包。因此，**有一张事务表不等于一项养成操作的所有资产已经原子提交**。[S05]

这会在进程故障、数据库故障或重试时形成可能的部分完成。本文没有在真实数据库上重现重复消费或复制，不把条件风险写成已发生漏洞。

`DbGuard` 的启动失败保护方向正确，也有玩家读取失败处理；但其主体是启动和登录保护，不能替代已经在线玩家的写入故障处理。TCP 端口可达也不等于 SQL 查询和提交已恢复正常。[S07]

**建议：** 列出“养成前余额、装备版本、扣除记录、产物、投递”各自的权威存储。能放同一数据库事务的放在一起；不能一起提交的，使用持久操作记录和补偿，不再以两次独立保存拼出业务事务。写库持续失败时暂停新资产变更，允许安全退出和只读查看。

**验收：** 每笔操作检查守恒式：期末资产＝期初资产＋已确认收益−已确认消耗。必须覆盖断库恢复和重复回调，而不是只测试正常扣除。

### A04｜快照是救援工具，但不是全账号经济回滚

`InvSnapService.apply` 恢复背包和末影箱。`trustCheck` 会检查带 P1 数据的装备 UID、所有者和状态，这是积极防护；但普通 NI 材料不走同样的物品身份检查，材料仓余额也不随背包快照一起回滚。[S08]

**条件风险：** 旧快照中的材料已经被存进仓库或花掉后，管理员恢复旧背包，旧材料可能重新出现，而仓库或消费所得仍保留。这需要管理员执行恢复，不是普通玩家随时可用的复制入口。恢复工具应主动提示并约束这种跨域不一致。

另一个明确的顺序问题：`applyPending` 在加载并确认恢复成功之前，先清除离线恢复请求。若快照加载失败、玩家再次掉线或恢复前快照失败，请求可能被消费但恢复未完成。[S08]

**建议：** 默认救援采用差异补偿，显示装备、材料仓、金币与交易记录之间的差异；不提供看似安全的盲目全量覆盖。离线请求只在恢复成功后标记完成，失败保留原因与可重试状态。恢复期间冻结该玩家的资产操作。

**验收：** 材料入仓后恢复旧快照、材料消费后恢复、装备入库后恢复、恢复中断和重复恢复都必须守恒。保留原快照只是可追溯，不自动等于防复制。

## 04 数值模拟：先让计算可靠，再扩大样本

### M01｜显式种子没有控制成员初始出手

`p1party.Member.__init__` 使用：

```python
self.next_swing = 1.0 + random.random() * 0.5
```

调用链给战斗传入 `Random(11)`，但这里调用的是模块级随机源，不是那个实例。`growthraid` 的对照组都传入同样种子，仍没有控制住这一步。[S09] [S10]

本轮精确摘取该短类重现：显式种子都为 11，首次出手分别为 **1.0873039367 秒、1.3772860441 秒**。测试另外固定全局种子，只是让本轮重现自身可复查；原调用仍没有把显式种子传入这个成员初始化。

**影响：** 即使配置和命令相同，结果也可能变化。已有报告将一部分变化解释为噪声之前，应先排除此随机源遗漏。不能仅靠增加几千局掩盖可复现性缺陷。

**修复与验收：** 构造器显式接收 RNG，禁止模拟代码偷用模块级 `random.*`。同配置、同种子重复运行，完整轨迹摘要和结果必须一致；额外调用全局随机数不得改变模拟输出。Python 官方也区分模块级函数和独立随机生成器实例。[S27]

### M02｜同样的 RNG 起点，不保证每一局抽到同一支队伍

`evaluate` 用同一个 RNG 先 `sample(pool, n)` 抽队，再把它交给 `run_party`。两种配装若改变战斗时长和随机调用次数，下一次抽队就会取到随机序列的不同位置。[S09]

本轮缩小重现只替换战斗为消耗一／两个随机数：第一组队伍相同，第二组开始不同。这不是完整战斗结果，而是对照设计的结构证明。

**建议：** 预先固定队伍名单和每局种子；队伍抽样、怪物编排、战斗、掉落至少使用独立随机流。配置比较时重用同一份队伍表。进一步需要精确配对时，以事件标识管理随机抽样，不能只相信相同初始 seed。

**验收：** 即使某配置让第一局提前结束，第 2～N 局的参战成员和初始条件仍完全相同。报告输出这些标识，避免只能看最后一张百分比表。

### M03｜多人焚烬的模型表示与实际规则不相同

团本模型在怪物字典中使用一个 `burn_by`，再次点燃会覆盖施加者。服务端则是每个玩家一个 `Session`、一个 `EmberSetEngine` 和独立 `EmberBurnBook`。[S09] [S11] [S12] [S13]

此外，服务端按每秒离散跳伤；模型按事件间隔累计连续伤害。对短命小怪、伤害击杀顺序、点燃刷新和触发活动效果，这不只是展示差异。

**本轮原始 Java 规则验证：** 两个玩家规则簿对同一目标分别点燃，每跳 10 与 20。500 毫秒时合计跳伤为 0；1,000 毫秒时为 30。若用一个 `burn_by` 保存后一个玩家，对应表示只能保留后者的 20；连续积分还可能在第一秒前就累计伤害。

这证明的是规则表示差异，**不是宣称真实团本总 DPS 一定少算三分之一**。实际差值还取决于人数、套装、刷新时刻、目标生命和其他伤害处理。

**建议：** 模拟燃烧采用 `(施加者, 目标)` 状态，镜像跳伤时间、快照、刷新与移除规则。以同一事件输入比较 Java 规则与 Python 模型。先复测单焚烬、双焚烬、三焚烬和混合队伍，再用结果调整数值；不要先削真实套装去适应错误模型。

### M04｜重点样本不是“全配装安全证明”

现有成长终验是有价值的重点回归，但第二排主要固定“破缀”，词条也使用特定组合。当前三套装、第一排三选一、第二排三选一、武器三个词条、护符三个词条，仅在第三排选对应套装的约束下，就有：

**3 × 3 × 3 × 3 × 3＝243 种结构。**

这个数还没有计入未点满、混阶、不同强化、不同成色、活动护符和多人组合。它不是要求做 243 套新玩法，而是提醒现有合法结构已超过九个样本。[S14] [S16] [S17]

另一个边界：`growth.py` 会把词条档位截到装备成色上限；标准参考装上，“请求四档”实际只生效一档。因此普通参考装的检查不等于最高成色极限检查。[S15]

**建议：** 先对合法结构做快速穷举，分别找单体输出、清群、恢复、承伤和经济的极值，再对极端候选跑完整模拟。不要只用 `DPS × EHP` 一个总分排序；多目标、续航、多人效果应保留各自的最坏情况。

**验收：** 报告实际生效套装、词条档位、成长投入、结构数、场景数、未覆盖范围。最高投入与正常推进装备分别测试；“封顶都开”必须在日志里能够看见。

### M05｜±3 个百分点是设计容差，不是统计证明

已有报告记录多轮调参，并将部分 +3.3～+3.6 接受为“约 3”；R03 还提到无战斗作用的勋记组合也产生了结果差异。[S16] 在 M01、M02 未处理前，不能把所有差异都解释为正常随机波动。

作为量级说明：若两组独立二项实验的真实成功率均约 50%，两组差值的近似 95% 区间半宽为 `1.96 × sqrt(0.5/N)`：每组 300 局约 **8.00 个百分点**，1,500 局约 **3.58 个百分点**，20,000 局约 **0.98 个百分点**。这些是示意算式，不是当前复用玩家池与配对设计的实际置信区间。

**建议：** 先修复确定性和对照，再输出变化的区间与按玩家聚类／按配对计算的误差。预先规定 ±3 的容差及例外政策；用未参与调参的种子、行为参数和配装作留出验证。多格同时扫描时，应报告整体越界情况，不能只挑最后一轮表现好的格子。

“没有显著差异”不等于“已证明等效”。要求等效时，应该检验区间是否落入容差，而不是把点估计刚好压到线内。

### M06｜同源配置有进步，但入口还没有真正统一

`p1config` 主要读取 `plugins/CoreRpg/`，发现 runs 副本差异时生成警告；`selfcheck` 会把该警告作为失败条件，这是已有正面措施。但 `p1party.raid_map` 和成长模块又直接读取 `CoreRpg/src/main/resources/`，其他模拟入口也可脱离 selfcheck 单独执行。[S09] [S15] [S19] [S20]

**本报告没有证明当前两份配置不同。问题是未来出现差异时，不同工具可能拿到不同输入。** 读取“真实文件”也不等于读取“正在运行那一份实际配置”。

**建议：** 构建时导出一个标准化规则快照，让模拟器和发布记录都引用其内容哈希。保留 Java 纯规则单测；避免长期依赖正则解析 Java 文本排版。每个裁决脚本启动时都必须校验输入，不只依赖有人记得先跑 selfcheck。

**验收：** 故意制造配置差异或不支持的值，所有裁决入口明确失败，而不是一边发警告一边生成看似可信的新表。

## 05 模拟的适用范围：不要让模型回答它没有建模的问题

### 5.1 行为参数不等于不同真人

当前模型用躲避、输出覆盖率、同时接怪数和技能命中数量描述操作行为。这样的抽象适合比较，但“600 个随机经历”不能被叫成“600 种真人”。默认补药、自动选装备、固定路线和投资策略会影响成长结论。[S09] [S19] [S28]

最小扩展不是再造复杂 AI，而是固定几类可解释行为：逐只稳打、集中清群、输出覆盖偏低、走位熟练但停手多、偏爱熟悉地图。输出覆盖、躲避与接怪数可相关，不能默认高躲避仍永远保持相同输出机会。

先做敏感性检查。若一个方案只在单一参数组合下成立，应标记“依赖行为假设”，而不是立即改全服。

### B03｜上界效果检查与完整经济检查必须分开

`growth.build` 按进度近似开放能力，Q07 之后可假设拿齐六点和全部指定勋记；`growthrun` 挂接效果。这有意提供战斗效果上界，却不是逐笔购买天赋、经历洗练、支付重置并做机会成本选择的完整过程。[S15] [S21]

`p2econ.raid_once` 的一条路径还使用按周给定的 `RAID_RATE` 来判团本成功，并非每次都根据当前实际配装重跑团战。它可作为经济情景假设，但修改团战规则后必须检查这张成功率表是否仍可用。[S22]

**建议分两份结果：** 第一份叫“解锁效果敏感性／上界检查”，用于找强度风险；第二份叫“真实成本成长模拟”，记录购买、洗练、失败、保底、储蓄、补给和消费冲突。不要用第一份结果宣称完整经济影响只变化零点几周。

**验收：** 同样初始资产下，每笔新增消费出现在总账；还应能比较“先升级装备”和“先洗词条”两个策略。高阶来源不能提前给低阶玩家使用。

### B04｜“最快两件极品周数”的名字会误导

`growthrun.two_week(..., at=30.0)` 找的是某条候选路线达到 **30% 玩家拥有两件极品**的时间，再按周线性插值；随后取路线中的最小值。[S21]

因此它不是平均毕业时间，不是 P50，也不是最快一名玩家所需时间。前轮讨论中未把这个区别讲清，本报告在此纠正。

**建议改名：** “候选策略中达到 30% 双极品拥有率的最早插值周”。同时给 P50、P90 或相应未达成比例、观察截止时点、从建号还是从 Q07 开始计时。未达成者不能从总体里悄悄删除。

不要把插值的两位小数当作同等精度的现实预测。约 0.1 周的变化可能小于行为假设和抽样误差。

## 06 成长与组合：把安全边界做硬，把主成长做实

### B01｜“拆分”不是文字描述的分身 +50%

当前“拆分”写对分身 +50%、对精英本体 −20%；配置分别是 `dmg_split=1.50` 与 `dmg_affix=0.80`。Java 的 `outMult` 对 `split` 目标同时乘两者，因此净倍率为 **1.20，即 +20%**。模拟也采用该层叠方式。[S17] [S18]

需要先由策划裁决到底想要哪个效果。若想分身净 +50%，应区分本体与分身的适用范围，而不是随便把数值抬高；若想净 +20%，应改明文说明。代码和模拟相互一致，仍可能一起违背业务意图。

**验收：** 以基准 100 伤害分别打普通怪、词缀本体、分身、首领，输出完整乘区；对本体和分身各设业务断言，不只测相乘函数。

### B02｜昂贵精修的体感偏弱，不应只靠文案解决

天赋三排首次费用合计 6,800 币，后续重置为 2,000 币；“余烬纹”最高档只增加燃烧／烬爆事件伤害 1%，不是总伤害 1%。当前已经增加适用说明和锁定洗练，不能再把“完全没有锁定”列成现存问题。[S17] [S23] [S25]

独立成本例：极品 T3、当前已有目标词条、保底从 0 开始、使用碎片锁定路线、不含勋记折扣，每次最高档概率 5%、第六次保底。期望次数为 `sum(0.95^k, k=0..5)=5.2982`，对应约 **5,298 币＋1,272 碎片**。这是锁定之后的边际成本，不含先获得目标词条的过程，不能直接与仓库从空词条开始的策略模拟混比。

同条件不锁类型时，指定满档词条的期望为约 **15.8945 次**。锁定机制确实改善了追求指定词条的成本；问题转向这份收益是否值得。

假设套装事件占总输出 20%，其伤害增加 1% 对总输出的直接增益约为 0.2%。这只是说明“分量增益”和“总增益”的区别，不是该服务器实测占比。

**建议：** 保留装备阶级、强化、觉醒承担明显变强；天赋和细词条作为低摩擦侧向调整或毕业后精修。验证前不继续扩充新的永久乘区。不要为追求小幅效果，叠加更多前置任务、货币和昂贵重置。

这不是建议立即大幅加强全部词条。先比较使用成本、可感知收益和不同场景价值；无体感的系统可以简化，而不是每次只增加解释文字。

### 6.1 套装数量少，不代表交互数量少

继续保留三套主线是合理的。当前已有天赋、词条、活动护符和条件性减伤／恢复，真正应控制的是 **同时生效的乘区、触发来源和状态转换**，而非只数套装名称。[S12] [S17]

建议写进规则的硬约束：同类易伤只取约定结果；禁止伤害事件无限再触发；明确套装计数是否允许受击推进；冷却在切装和重连时不被清空；恢复的来源、频率和总量可追踪；临时活动不能无审查地变成第四个长期战力槽。

每新增一个效果必须给出“能与什么叠、不能与什么叠、最高投入时上限、多人时归属”。这是减少失控组合的方法，不要求玩家研究更多搭配。

## 07 实服、地图与分工：保持轻流程，但交付必须有边界

### Q01｜9/9 是基础功能检查，不是所有新玩法验收

当前 gameplay 报告的九项是登录、主菜单、熔炉、附魔、钓鱼、图腾、盾牌、合成、世界规则／怪物。它对基础环境有价值，但不覆盖 1.62.0 仓库异步交付、全部套装组合或完整团本平衡。[S24]

仓库也有成长专项补测，不能反向说“完全没测试”。只是需要区分：纯规则测试、管理员造条件的冒烟、削弱怪物后的路线／结算检查、正常强度实服战斗、真人体验，各自证明的事情不同。[S02] [S25]

**建议每份结论只写四项：** 测试版本、是否使用管理员辅助、覆盖范围、仍未覆盖。不要新增一套冗长审批流程；一段明确元数据足够避免证据被误用。

对随机失败的测试，重跑可以用于诊断，但原失败必须保留。长期“重跑即过”会把不稳定测试伪装成稳定测试。

### 7.1 地图分工应保留，但本轮不能替视觉质量背书

本轮没有取得实际世界存档和完整视觉验收证据。源码或生成脚本能说明建设意图，路线检查能说明可达性，都不能单独证明地图好看、视野清楚、多人不卡或首领攻击范围匹配。

交给地图 AI 的输入应是已冻结的空间约束：房间范围、地板高度、通道净空、门洞、出生点包围盒、首领不可放装饰区、危险范围和观战／复活点。它负责地形、建筑、材质与灯光，不擅自改掉落和机制。

Grok 接回地图后负责坐标接入、实例复制、刷怪、门与结算。必须在最终复制出的实例里验证，而不是只在建造世界里跑。模型若未模拟地形，就不能用模拟通关率否认地图卡位造成的真实问题。

最低交付证据为：俯视路线、关键玩家视角、正常装备实走、多人会车、首领出生／转身与预警范围；渲染好看和功能通过分别判定。

### Q02｜需要一个可复查的发布凭证

当前 HEAD 的版本是 1.62.0；交接仍把 1.61.0 标为在线，并另列未部署改动；新仓库 STATUS 使用“上线内容”表述。这不证明有人误报，但显示仅看一个文件很容易混淆“已提交”和“已部署”。[S01] [S02] [S03]

GitHub 分支查询在本轮返回 `protected: false`，且没有列出必需状态检查。这是本次观察到的分支响应，不是完整组织权限审计；本次也没有替你改变任何保护规则。[S26]

**建议：** 每次发布保留一份清单：源码 SHA、插件版本、JAR 哈希、规则版本和哈希、地图版本和哈希、存储版本、测试报告、实际部署时间、回滚包。数据恢复还要能重放未完成事务，不能只保存旧 JAR。

多人／多 AI 写同一工程时，用独立任务分支和小 PR；数值或存储改动要求针对性检查。无需每一行文案都组织审批。分支保护可要求检查，但要确保失败、跳过和未覆盖被正确区分。[S29]

## 09 不推倒重来：三个整改工作包

### 工作包一：资产可靠性，优先于新增养成

范围是 A01～A04。插件负责人补持久交付记录、失败补偿与恢复对账；测试负责人在隔离环境做断线、断库、重启与重复请求。不要同时改奖励概率或强化数值，避免无法区分资产错误与平衡变化。

**完成标准：** 正常、失败、重试三个路径都守恒；未完成请求可以查询并自动恢复；离线结果不依赖人工翻日志。相关新仓库功能没有完成这些检查前，不把其“上线内容”标记当作安全证明。

### 工作包二：模拟可信度，不先微调玩法

先修 M01～M03，再扩 M04、M05 的对照和极值检查。保留一份修复前的配置，比较修复模型而不改规则时结果改变多少；这部分差值属于模型修正，不能算作策划加强或削弱。

**完成标准：** 相同输入可复现；配置与轨迹可追溯；Java／Python关键规则一致；报告覆盖边界与区间；至少用正常强度的单人和多人战斗记录校准一次。涉及多人焚烬的旧结论应重新计算。

### 工作包三：成长体感与可玩内容

在前两包可依赖之后，审查 B01～B04。只选几个代表投入节点比较“升级前后打得更快／更稳多少、花了多少资源”。把主成长和毕业精修分开，不靠增加系统数量解决体感不足。

地图方继续完善现有地图，而非同时扩新世界；评审方记录正常装备实战和真实玩家意见，不替实现方验证自己的宣传语。

**完成标准：** 每个昂贵成长节点有明确收益和成本解释；没有只在特定模拟参数下成立的主线结论；地图观感、战斗、奖励分别有证据。不能用所有人都点了某天赋证明其好玩，也不能用通关率几乎不变证明其值得购买。

### 分工只需要四个责任，不需要更多审批层

| 责任 | 核心交付 | 禁止替代 |
|---|---|---|
| 策划／服主 | 规则意图、代价、硬边界 | 不让实现者自行补奖励数字 |
| 插件实现 | 可恢复业务流程、权威规则 | 不用文案代表功能完成 |
| 数值模拟 | 对照、极值、区间、假设 | 不把模型结果冒充真人数据 |
| 独立验收＋地图交付 | 实例实走、故障、正常战斗与画面 | 不以削弱冒烟替代平衡验收 |

任务可以小步提交，但每个工作包只在完整链路成立后关闭。不要重新回到“每改一行注释就结一个里程碑”，也不要因风险清单很长就同时重写全部模块。

## 10 给 Grok／接手者的执行摘要

先核对本报告基线之后的提交。本报告是针对 `4044125` 的观察，不是要求覆盖更新代码。每项整改都应记录“仍存在／已经修复／规则另有裁决”和证据。

**立即应做：** 给装备库自动入库和离线交付补持久状态；补快照与仓库对账；修模拟的全局 RNG、抽队流和多人燃烧表示；为“拆分”的本体与分身效果作明确裁决。

**随后应做：** 穷举合法结构后筛极端组合；输出真实生效档位与置信区间；把成长上界检查、真实成本模拟和 30% 双极品阈值分别命名；对正常强度实服样本作校准。

**暂不做：** 第四套装、新的永久战力槽、更多独立乘区、大规模调低／调高全部装备、重新设计整个新手剧情、以增加日课数量延长毕业时间。

**最终判断：余烬已经建立了有价值的 AI 协作与数值验证基础。下一步的创新不在于让它算更多次，而在于让“规则、模拟、真实战斗和资产账本”彼此核对。先让结果可信，再让内容增长。**
